## 2. 输入和回包

分别以 `markdown` 和 `structure` 创建一个逻辑条目。以 Markdown 组为例：

```markdown
MARKDOWN_HEAD_SENTINEL

- MARKDOWN_TAIL_SENTINEL
```

受控 kernel 将其按历史“段落 + 列表”形状存为两个兄弟块，并返回：

```json
[
  {
    "doOperations": [
      {"id": "20261018080001-head001"},
      {"id": "20261018080002-tail002"}
    ]
  }
]
```

首块 Kramdown 为 `MARKDOWN_HEAD_SENTINEL`，尾块为 `- MARKDOWN_TAIL_SENTINEL`。内存中没有删掉尾块或伪造读取失败；两个块均可通过 kernel 的按 ID 读取接口读到，尾块最初没有条目属性。

## 3. 两组实际结果

| 检查 | Markdown 组 | Structure 组 | 含义 |
| --- | --- | --- | --- |
| 创建回执 | `ok=true` | `ok=true` | 输入已被接受，未提示多块不完整 |
| `setBlockAttrs` 调用 | 仅首块 ID | 仅首块 ID | 尾块没有条目逻辑 ID、类型和元数据 |

| `getStoredItemKramdown` | 仅 `MARKDOWN_HEAD_SENTINEL` | 仅 `STRUCTURE_HEAD_SENTINEL` | 编辑/导出的基础读取缺尾块 |

| 真 `ActionExecutor.run(item, "copy")` | `ok=true`，内存剪贴板仅首块 | 同左 | 确认问题经过实际执行器，非只推断计划 |

这证明的是“**给定已记录的真实内核返回形状，当前真实生产服务会成功回执但丢失条目级完整性**”。尾部并非一定从思源物理文档中消失，风险在于用户通过条目的检索、预览、复制、编辑、导出和删除无法完整管理它。应避免笼统写成“思源全部原文被删除”。

本轮新加入的导出读取失败/体积拒绝检查解决的是“已识别条目的正文是否取得、包是否超限”；它不能自动修复这个更早发生的条目边界问题。不能把两类完整性混成一项已解决。

## 4. 影响及本轮没有证明的事

- 对新增的多段 Markdown、结构组合、整文档捕获及多块模板包，已确认存在上述服务风险；调用输入虽有合法 `itemType`，不代表整体内容已形成一个可管理锚点。
- `text` 类型同样通过 `appendBlock` 的 Markdown 入口写入；含空段/特殊 Markdown 的输入可能拆块。此次只执行 `markdown`/`structure` 两组，不能把每种文本分行规则或每条现有模板都说成已实测失败。
- 此次没有执行 SiYuan Markdown 解析器；“哪一段具体 Markdown 在当前各版本拆为几个块”来自历史形状加静态推断，没有新增宿主矩阵。单块代码围栏、真实 superblock、引用目标多块读取等需分别验证。
- 没有运行真实系统剪贴板、浏览器 UI、宿主插入、更新或恢复迁移；`updateBlock` 的实际拆块形状和回滚行为也未在本次验证。当前创建路径缺陷不能被描述成所有更新路径已证明相同。
- 没有扫描用户常用库，也没有判断用户历史内容是否已受影响。禁止自动把邻接兄弟块猜作某个条目的正文，或按模板标题批量清理；真实库中可能混排用户手写内容。
- B-005 限制不因离线复现而解除。仓库承诺的 superblock 包装/剥壳尚未在当前生产源码找到，不应在缺少验证时仓促引入新存储格式并宣布修复。

## 5. 最小安全止损建议与代价

| 方案 | 能阻止什么 | 代价或需要避免的问题 |
| --- | --- | --- |
| 立即在捕获/编辑/导入/帮助标明“多块正文完整性未完善”，停止推荐导入新的复杂多段示例；旧数据保持可查看来源 | 防止用户把已知缺陷当作可靠模板/备份能力；不改变既有数据 | 只提示不能杜绝继续产生部分条目，不能称为生产修复 |
| **写前保守禁用无法证明为单一锚点的新增、正文更新和导入**，保留已有条目只读、来源打开和导出已有内容的明示路径 | 可以在零写入前截断已知高风险输入；适合作为暂时防护 | 会牺牲多段模板、文档捕获和结构场景；仅匹配 `\n\n` 不够，标题/列表能在其他换行形式分块，代码中空行又可能属于单块。若没有经验证的宿主等价解析器，不能把启发式检测说成完整防护 |
| 写后检查返回的操作和实际新块归属，发现新增多个顶层兄弟时给出“部分创建/需恢复”回执及明确 ID | 避免再次报普通成功，便于定位真实残余 | 已经发生写入；不能仅改成普通失败让用户重试，否则可能反复追加。需要幂等的部分成功状态和安全恢复设计；不能把 `doOperations.length > 1` 一概当成多个顶层块，也不能未经关系核验盲删全部操作 ID |

近期优先保留诚实标注并收紧复杂示例扩充；若要立即阻止继续制造不完整条目，写前保守禁用比写后普通失败更容易控制，但须接受场景暂不可用。根本修复应单独立项：确定一个真实锚点容纳完整条目的格式，覆盖 create/update/import/rollback/read/index/copy/export/remove 全链路，并规划既有拆散内容的非猜测恢复方法。

根本方案验收必须包含：单段对照、多段段落、标题/列表/任务、围栏代码、包含变量的模板、嵌套结构；用真实内核读回完整正文与父子关系；覆盖属性失败和正文更新失败后的回滚；门禁负向真实注入后失败并恢复通过。在这些证据完成前，“结构完整可用”“模板包导入后整体可调用”“删除无残余”等声明都应保持未完成。

## 6. T-0090 / R237 离线止损实现（尚待真实宿主验收）

本轮随后采用保守的锚块清单方案：新建条目收集同一次 `appendBlock` 回包中的全部合法物理块 ID，并在首块写入 `custom-xlc-parts`（逗号分隔、首块优先）。正文读取、索引摘要、导出、条件撤销和删除按该清单逐块处理；属性写入失败时回滚同批全部块；清单损坏、重复、首块不匹配或超过 64 块时显式失败。受控内核契约已覆盖完整读回、整体删除、属性失败全量回滚和损坏清单拒读。

这项实现只约束新写条目，不能修复旧条目，也没有把多块正文更新伪装成可用：当前 `updateItem` 对带 `parts` 的正文更新返回 `conflict`，等待真实 `updateBlock` 的拆块回包和恢复语义。B-005 仍阻止真实宿主验收；因此 `custom-xlc-parts` 的返回顺序、同一库归属、真实回读和删除仍不能视为已验证。旧相邻块继续只提供人工核对和来源打开路径，不自动合并或清理。
